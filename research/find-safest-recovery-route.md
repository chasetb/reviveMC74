# Recovery research: Meraki-logo state after `installApps`

Context: [Find the safest recovery route from the Meraki-logo state](https://github.com/chasetb/reviveMC74/issues/3).

## Baseline and scope

The recorded baseline is ClockworkMod Recovery (CWM) 6.0.4.7 reachable by holding Mute during boot, no device in `adb devices`, no original boot/recovery/system backups, and Fastboot entry or enumeration unverified. The last completed script objective is unknown. This note is research only; no device commands were run.

## Findings

- **A Meraki logo does not identify the failure.** In [Anyone have a pre-built system image?](https://www.reddit.com/r/ReviveMC74/comments/1mu907l/anyone_have_a_prebuilt_system_image/), the poster reports reaching `installApps`, then seeing the Cisco/Meraki logo and losing host connection until returning to recovery. That is an observed symptom, not a diagnosis; the post’s comments could not be verified.
- **`installApps` is a system-changing step, but the current code does not reboot at its end.** [`installAppsFunc`](https://github.com/chasetb/reviveMC74/blob/main/reviveMC74.py#L583) first asks for normal Android mode, then removes system apps, pushes files under `/system`, changes `/system/bin/click`, installs APKs, and updates the launcher. A direct `installApps` request from recovery first passes through [`adbModeFunc("normal")`](https://github.com/chasetb/reviveMC74/blob/main/reviveMC74.py#L735): if Fastboot is not detected, it sends `adb shell echo b >/proc/sysrq-trigger` and polls for normal ADB. With no ADB enumeration, that shell request cannot be sent and the install function returns before its install operations. This describes the present code path; it does not establish what happened in an earlier run or on the reported Reddit device.
- **Do not use the aggregate `revive` objective as a diagnostic.** [`reviveFunc`](https://github.com/chasetb/reviveMC74/blob/main/reviveMC74.py#L255) calls `flashPartFunc()` before `installAppsFunc()`; [`flashPartFunc`](https://github.com/chasetb/reviveMC74/blob/main/reviveMC74.py#L495) writes an image to a device partition (boot by default).
- **Upstream reports show more than one failure mode.** [Script failing at ADB Reboot (InstallApps)](https://github.com/reviveMC74/reviveMC74/issues/7) reports a reboot-stage failure; one commenter reported success after freeing space under `/data`, but that anecdote does not establish the cause of the logo report. [Phone won't boot after fixPart](https://github.com/reviveMC74/reviveMC74/issues/12) reports a Meraki-logo hang after a modified boot image, with CWM still reachable; its discussion says ADB-requested reboot could hang in CWM and that rebooting from CWM’s menu worked for that reporter. [Phone is basically bricked](https://github.com/reviveMC74/reviveMC74/issues/16) also describes a non-booting OS with CWM/ADB access, but no common cause is identified. These are separate reports, not a diagnosis for this MC-74.
- **Recovery and Fastboot enumeration are distinct observations.** The repo detects `recovery`/normal state from `adb devices` and Fastboot from `fastboot devices`; its fastboot parser supports both older `fastboot` and newer `Android Fastboot` output ([`findFastbootLine`](https://github.com/chasetb/reviveMC74/blob/main/reviveMC74.py#L221)). Android’s [ADB documentation](https://developer.android.com/tools/adb) notes that an ADB `device` state can appear while Android is still booting, so enumeration alone does not prove a usable home screen.

## Least-risk checks and CWM workaround

For diagnosis, record the actual screen and CWM version, then use only host-side enumeration (`adb devices -l` and `fastboot devices`) with the known USB connection. Save the exact outputs and current local `reviveMC.log` if available, with serials and private paths redacted before sharing. Treat `recovery`, `device`, a Fastboot line, and no line as different observations. Check the cable/connector and host USB visibility if neither tool lists a device. Do not infer Fastboot support from the current baseline, and do not issue reboot, flash, install, erase, or partition commands as part of these checks.

The repo’s CWM workaround is in [`adbModeFunc`](https://github.com/chasetb/reviveMC74/blob/main/reviveMC74.py#L757): it avoids `adb reboot` (commented as hanging in CWM) and sends `echo b >/proc/sysrq-trigger` through ADB shell to force a reboot. The [Linux kernel SysRq documentation](https://docs.kernel.org/admin-guide/sysrq.html) says `b` reboots immediately without syncing or unmounting disks. The workaround therefore requires usable ADB shell access and a working kernel SysRq handler; it is a force reboot, not a read-only check or a repair. The baseline has no ADB enumeration, so this path is not currently confirmed usable. A CWM menu reboot is reported to have worked for one upstream reporter, but it is not proof of the state or safest action for this device.

**Stop before any partition write.** Original backups are absent and Fastboot is unverified. The available evidence supports preserving CWM access and collecting read-only state first; it does not support flashing, restoring, or attributing the logo to a particular partition. The hard gate remains verified original backups plus a demonstrated recovery route before writes.
