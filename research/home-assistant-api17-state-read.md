# Home Assistant state read on Android API 17

Research for [Validate an API 17 Home Assistant state-read path](https://github.com/chasetb/reviveMC74/issues/14), checked 2026-11-17. The owner's unique Home Assistant Cloud hostname is intentionally omitted. No token was obtained or sent, and no device or Home Assistant configuration was changed.

## Finding

The [chosen interaction](https://github.com/chasetb/reviveMC74/issues/13#issuecomment-6956098079) is one read of `binary_sensor.front_door_door` on each load, displaying `OPEN` for `on`, `CLOSED` for `off`, and `UNAVAILABLE` for errors or unknown state. Home Assistant provides exactly this read through authenticated `GET /api/states/<entity_id>`; its [REST documentation](https://contributors.home-assistant.io/core/internals/rest-api/) says each request needs an `Authorization: Bearer` token and the endpoint returns one entity or 404.

The owner's LAN address uses plain HTTP. HTTP does not protect the bearer token in transit, so that address is not a secure credential route. The owner also has a Home Assistant Cloud HTTPS address. An unauthenticated host-side GET to its state endpoint returned HTTP 401, confirming that the path is reachable and requires authentication; no credential was sent. This does not prove that Android 4.2.3 can connect.

**No secure direct path on the MC-74's stock API 17 TLS stack is established.** Android's [SSLSocket compatibility table](https://developer.android.com/reference/javax/net/ssl/SSLSocket) lists TLS 1.2 as supported from API 16 but enabled by default only from API 20. It lists AES-GCM cipher suites from API 20, while API 17 offers older CBC suites. A host-side TLS 1.2 probe of the current Cloud endpoint succeeded with `ECDHE-RSA-AES128-GCM-SHA256`, P-256, and RSA PKCS#1 SHA-256. A probe restricted to `ECDHE-RSA-AES128-SHA`, `ECDHE-RSA-AES256-SHA`, `AES128-SHA`, `AES256-SHA`, and `DHE-RSA-AES128-SHA` ended before handshake. The probe is evidence about the endpoint's behavior with those offered suites, not a substitute for testing the MC-74's actual provider.

The Cloud endpoint currently serves a Let's Encrypt YR2 chain ending at ISRG Root X1. The leaf was valid from 2026-09-17 to 2026-12-16 in the host-side probe. [Let's Encrypt's compatibility documentation](https://letsencrypt.org/docs/certificate-compatibility/) lists Android 7.1.1 or newer for built-in ISRG Root X1 trust, so the MC-74's stock Android 4.2.3 trust store cannot be assumed to validate this chain. [Let's Encrypt notes](https://letsencrypt.org/2020/11/06/own-two-feet/) an app can carry ISRG Root X1; that can address trust, but cannot add a missing cipher. Never replace certificate and hostname checks with a trust-all manager.

## Credential and APK constraints

- Home Assistant's [authentication API](https://contributors.home-assistant.io/core/internals/auth-api/) says long-lived access tokens are valid for ten years and are used as bearer tokens. A token belongs to a user, not to this single GET. Home Assistant's [permission policy](https://contributors.home-assistant.io/core/internals/permissions/) has a read-only group that can read **all** entities; the ordinary Users group can control them. A dedicated read-only identity would limit control privileges but would not confine disclosure to the front door entity. Confirm the available account setup before issuing a token.
- API 17 predates the [AndroidKeyStore key-pair API introduced at API 18](https://developer.android.com/reference/android/security/KeyPairGeneratorSpec). [Android's storage guidance](https://developer.android.com/training/data-storage/app-specific) says internal app files are isolated from ordinary apps, while automatic encryption of those locations is an Android 10+ feature. This MC-74's verified root recovery ADB can read `userdata`; persistent app storage is therefore not a safe vault against anyone with recovery access. Keep tokens out of the APK, repo, logs, command history, and public issues. A memory-only token avoids storage but would require re-entry after restart; persistent storage requires explicit acceptance of the device-access risk and prompt revocation if it is lost.
- An APK must declare `minSdkVersion` no higher than 17 and use only APIs available on that platform; Android's [uses-sdk documentation](https://developer.android.com/guide/topics/manifest/uses-sdk-element) describes the install-time API check. The [ADB documentation](https://developer.android.com/tools/adb) supports installing a built APK with `adb install` on a connected Android device. The repo's `installApps` objective also removes and modifies existing system apps, so it is unsuitable for a one-app validation; use a separate signed APK and normal-boot ADB after the agreed boot gate. Installation changes `userdata`, so record package name and uninstall/revoke steps before trying it.

## Gate before calling the route viable

1. Complete the [modified boot and rollback checkpoints](https://github.com/chasetb/reviveMC74/issues/12#issuecomment-6955930652) and reach a usable Android 4.2.3 UI with normal-boot ADB. Confirm date/time, LAN/DNS reachability, and actual API level. No app installation is part of this research ticket.
2. On this MC-74, without a token, log supported and enabled TLS protocols/ciphers, test a verified handshake to the intended HTTPS endpoint, and capture the negotiated protocol/cipher plus certificate chain and hostname result. If the stock shell lacks a suitable TLS client, a temporary signed, token-free API 17 probe APK may perform this check after the boot gate; record its package name and uninstall it afterward. A failed handshake or untrusted chain is a stop; do not fall back to LAN HTTP or disable verification.
3. If a supported TLS provider or compatible HTTPS bridge is chosen later, repeat the test on-device with its exact endpoint and trust configuration. Only then provision a dedicated read-only identity if available, through a private channel, and verify one authenticated GET. Fail closed on 401, timeout, `unknown`, `unavailable`, or malformed JSON.
4. Install the final minimal API 17 status APK only after the transport gate. Check physical door open/close against fresh reads and the `UNAVAILABLE` state on failure. Record package removal and token revocation as the app rollback. A host-side 401 and successful modern TLS handshake are insufficient evidence for this step.

## Decision edge

The current LAN endpoint is insecure for a bearer token. The existing Cloud endpoint is a candidate only after an API 17-capable, certificate-verifying TLS path is demonstrated; stock API 17 lacks the successful GCM suite and likely cannot negotiate the tested Cloud configuration. The next decision is whether a maintainable modern TLS provider or a controlled HTTPS bridge can supply that path, or whether the Home Assistant interaction must stop at this gate.
