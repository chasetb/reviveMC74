# MC-74 boot2 and system2 rollback research

Research for [issue #10](https://github.com/chasetb/reviveMC74/issues/10), within the [MC-74 firmware and Home Assistant map](https://github.com/chasetb/reviveMC74/issues/1). Checked 2026-11-16. The device observations below were gathered read-only in CWM recovery on 2026-11-16; no partition was written. The full ADB transcript was not retained separately, so the observed commands and results are recorded here.

## Finding

**The default Revive path writes both `boot` and `boot2`; it modifies files under `/system` and `/data`, with no default-path write to `system2`.** This does not establish which boot slot the MC-74 bootloader selects or how a Meraki OTA would select or update slots. For a conservative rollback set, save distinct original images of `boot`, `boot2`, `recovery`, `system`, and `userdata`; also capture `system2` until the bootloader/OTA slot behavior is established. The repository's install path changes `/system` and `/data`, so a system-only snapshot would not restore the full pre-install state. No image has yet been saved and integrity-checked, so the map's backup safety gate remains closed. ([issue #1 gate](https://github.com/chasetb/reviveMC74/issues/1), [issue #8 capture result](https://github.com/chasetb/reviveMC74/issues/8#issuecomment-6939401473))

## Device evidence

Read-only CWM observations for this device on 2026-11-16:

| Check | Observed result |
| --- | --- |
| `adb shell id` | uid 0 |
| `adb shell cat /etc/recovery.fstab` | Names primary `boot`, `recovery`, and `system`; does not name `boot2` or `system2`. |
| `adb shell ls -l /dev/block/platform/sdhci.1/by-name` | `boot` → `mmcblk0p15`; `boot2` → `mmcblk0p16`; `system` → `mmcblk0p17`; `system2` → `mmcblk0p18`; `recovery` → `mmcblk0p21`. |
| `adb shell cat /proc/partitions` | `boot` and `boot2`: 8,192 1K blocks each (8 MiB); `system` and `system2`: 518,144 1K blocks each (530,579,456 bytes); `recovery`: 16,384 1K blocks (16 MiB); `userdata` (`mmcblk0p24`): 995,328 1K blocks. |
| `adb shell cat /proc/mounts` | Only `/cache` was mounted. |

The map and sizes identify separate block nodes, but do not reveal which boot node is active or whether the device has an automatic fallback/update policy. The previous issue #8 record also says `adb pull` of `boot` to host `/dev/null` transferred 8,388,608 bytes, but deliberately discarded the data; it did not create or hash an image. Recovery and system transfers had not been performed in that record. [Issue #8 resolution](https://github.com/chasetb/reviveMC74/issues/8#issuecomment-6939401473)

## What the checked-in Revive code changes

The source links below are pinned to the repository revision used for this research: [`1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d`](https://github.com/chasetb/reviveMC74/tree/1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d).

- The default partition argument is `both`, and `reviveFunc` calls `flashPartFunc` before `installAppsFunc` ([default and orchestration](https://github.com/chasetb/reviveMC74/blob/1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d/reviveMC74.py#L77-L80), [revive path](https://github.com/chasetb/reviveMC74/blob/1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d/reviveMC74.py#L254-L268)).
- With `part=both`, `fixPartFunc` builds one patched `boot` image and `flashPartFunc` writes that image first to `boot`, then to `boot2` ([fix selection](https://github.com/chasetb/reviveMC74/blob/1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d/reviveMC74.py#L405-L421), [write targets](https://github.com/chasetb/reviveMC74/blob/1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d/reviveMC74.py#L495-L555)). Thus `boot2` must be included in any rollback of the current Revive write set, even if it is not the active boot node.
- `backupPartFunc` also changes `both` to `boot`, so its default capture does **not** save `boot2`. It stages a copy under `/cache`, pulls it to the host, and removes the staged file ([backup path](https://github.com/chasetb/reviveMC74/blob/1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d/reviveMC74.py#L343-L400)). This is not a full baseline backup.
- `replaceRecoveryFunc` can flash the CWM image to `recovery`; `backupPartFunc` calls it before beginning its capture. Preserve the pre-change recovery image before any run that can replace recovery. The live environment is CWM; a capture now would preserve the current CWM recovery, and the evidence does not establish that an original stock recovery image was saved. When CWM is already installed, this code may skip the fastboot write, but it still does not automatically preserve an earlier stock recovery image ([recovery replacement](https://github.com/chasetb/reviveMC74/blob/1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d/reviveMC74.py#L271-L339), [backup ordering](https://github.com/chasetb/reviveMC74/blob/1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d/reviveMC74.py#L343-L360)).
- `installAppsFunc` removes and installs files under `/system`, changes `/system/bin/click`, installs/uninstalls apps under `/data`, and updates launcher state; the boot-flash path also writes metadata under `/data`. Preserve `system` and `userdata` to restore these changes ([install operations](https://github.com/chasetb/reviveMC74/blob/1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d/reviveMC74.py#L583-L674), [boot metadata](https://github.com/chasetb/reviveMC74/blob/1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d/reviveMC74.py#L560-L578)).
- The default `revive` path does not target `system2`. The generic manual `flashPart` objective accepts a caller-supplied partition name, so an explicit `part=system2` is possible outside that default path. The script reads `u-boot-env` only to extract the device serial number and records metadata for cached `update.tar.gz`, `boot.img`, and `system.img`; those metadata reads do not explain image application or boot-slot selection ([manual target construction](https://github.com/chasetb/reviveMC74/blob/1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d/reviveMC74.py#L495-L510), [environment read](https://github.com/chasetb/reviveMC74/blob/1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d/reviveMC74.py#L865-L887), [update-file metadata](https://github.com/chasetb/reviveMC74/blob/1863ecac66aa3d5a3edd4b7a40fa9cccadcdcf9d/reviveMC74.py#L905-L911)). No public MC-74-specific bootloader or OTA primary source was found that closes this gap.

## Capture and rollback limits

Direct `adb pull <verified-by-name-node> <host-file>` is the candidate host-side capture method. AOSP's Android 4.2.2 ADB client accepts block-device sources, while the device sync service opens the remote node read-only and streams it to the host ([ADB client](https://android.googlesource.com/platform/system/core.git/%2B/android-4.2.2_r1/adb/file_sync_client.c#L947), [device sync service](https://android.googlesource.com/platform/system/core.git/%2B/android-4.2.2_r1/adb/file_sync_service.c#L323), [ADB file-copy docs](https://developer.android.com/tools/adb#copyfiles)). The device-specific success recorded so far proves only that a boot transfer to `/dev/null` completes; it does not prove saved images for all listed nodes. `/sdcard` is not a viable backup destination in the observed recovery, and no removable SD route is available ([issue #9](https://github.com/chasetb/reviveMC74/issues/9#issuecomment-6939022258)).

Before opening the safety gate, capture each needed node directly to a distinct host file, check every file's exact byte size against the current device map, calculate host SHA-256 hashes, and retain a second copy and the command log. Capture `system2` as a precaution, but do not claim it is part of the current Revive write set. Capture `userdata` when rollback must restore app and launcher data; it is not a substitute for the separate `system` image. Do not write partitions or start a CWM backup to device storage under the current gate.

**Unresolved:** the MC-74 bootloader's selected boot node, any slot-fallback rules, and vendor OTA write behavior. The current evidence supports the Revive script's write set, not those firmware behaviors. The user must treat the safety gate as closed until all required originals are actually saved and checked.
